# 방법: staged-insight-research

- id: staged-insight-research
- name: 단계형 인사이트 리서치 (1차 조사 → 2차 확장 → 3차 포커스 인터뷰)
- mode: staged
- when-to-use: 하나의 GOAL(채널 컨셉 결정, 오퍼/카피 설계, 재방문 트리거 발굴 등)을 위해 광범위 조사→확장→심층 인터뷰를 축적식으로 진행하고, 결과를 프로젝트 단위로 저장해 후속 작업이 이어받아야 할 때. 단계가 나뉘어 있으므로 하루에 다 못 끝내도 됨.

## 설계 철학 — 자유도 우선

이 문서는 스크립트가 아니라 **가드레일**이다. [HARD]로 표시된 것만 지키면,
나머지는 실행자가 GOAL과 상황에 맞게 재량으로 판단한다 ([FREE]).
단계를 병합하거나(예: 조사량이 적으면 1+2차 통합), 표본 수를 조정하거나,
질문 스타일을 바꾸는 것은 모두 허용된다 — 단, 그렇게 판단한 이유를 manifest에 한 줄 남긴다.

## [HARD] 저장 규약 — 이것이 이 방법의 존재 이유

모든 산출물은 프로젝트 디렉터리에 저장한다:

```
history/outputs/research/{project-id}/
├── manifest.json      ← 프로젝트 상태의 단일 진실 공급원
├── phase1-broad.md    ← 1차 조사 결과
├── phase2-extended.md ← 2차 확장 조사 결과
├── phase3-focus.md    ← 3차 포커스 인터뷰 결과
├── summary.md         ← 전체 요약 (후속 작업의 기본 진입점)
└── raw/               ← (선택) 페르소나별 원본 응답 등 부속 파일
```

- `project-id`: 케밥케이스 슬러그 (예: `ai-parenting-channel-2607`)
- **시작 시**: manifest.json이 있으면 Read 후 이어서 진행(재개), 없으면 생성
- **각 단계 완료 시**: 해당 phase 파일 저장 + manifest의 단계 status 갱신 — 이 두 가지는 절대 생략 금지
- **전체 완료 시**: summary.md 저장 + 위키에 `project_{project-id}` 페이지로 요약·경로 링크만 저장 (5KB 제한 준수, 본문 복붙 금지)

### manifest.json 형식

```json
{
  "project_id": "ai-parenting-channel-2607",
  "goal": "AI 시대 육아 교육 채널의 주제·컨셉 결정",
  "created": "2026-07-11",
  "updated": "2026-07-11",
  "phases": {
    "phase1": { "status": "done|in-progress|pending|skipped", "file": "phase1-broad.md", "date": "", "note": "판단 메모 (병합/생략/표본조정 이유 등)" },
    "phase2": { "status": "pending", "file": "phase2-extended.md", "date": "", "note": "" },
    "phase3": { "status": "pending", "file": "phase3-focus.md", "date": "", "note": "" }
  },
  "summary_file": "summary.md",
  "external_data": [],
  "downstream_hints": ["이 조사를 소비할 후속 작업 힌트 (예: 채널 컨셉 기획서, 랜딩 카피)"]
}
```

## [HARD] 리서치 설계 프레임 — GOAL → KNOWLEDGE → SEGMENT → QUESTION

어떤 단계든 질문을 만들기 전에 이 역산 구조를 먼저 세운다:

1. **GOAL**: 이 리서치가 끝나면 무엇을 결정/제작할 수 있어야 하는가 (한 문장)
2. **KNOWLEDGE (K1..Kn)**: GOAL에 필요한 지식 항목 + 각 K를 "누가(어떤 세그먼트가)" 답할 수 있는지 명시
3. **SEGMENT**: K를 답할 대상을 우선순위 테이블로 특정 (인구통계는 목적이 아니라 프록시)
4. **QUESTION**: 질문마다 K-태그와 산출 용도(이 답이 어디에 쓰이나)를 붙인다.
   선다형/추상형 원본 질문은 그대로 쓰지 말고 "체험된 구체적 순간 + 그 순간의 자기대화"를 캐묻는 질문으로 변환한다.

## 3단계 개요 ([FREE] — 세부는 재량)

### 1차 조사 (Broad) → phase1-broad.md

- 목적: K별 지형 파악. 세그먼트 간 차이가 어디서 갈라지는지 발견.
- 권장: 구조화 설문(척도·순위·복수선택) 위주, 세그먼트당 페르소나 10~30명 수준. 규모는 GOAL 중대성에 맞게 재량.
- 산출: K별 응답 분포, 세그먼트 비교표, "2차에서 확장할 축" 후보 목록.

### 2차 확장 조사 (Extended) → phase2-extended.md

- 목적: 1차에서 갈라진 축을 넓혀 검증. counter-case(반대 사례) 수집 포함.
- 권장: 1차에서 흥미로웠던 세그먼트의 표본 확장 + 인접 세그먼트 추가. 1차 결과가 이미 명확하면 축소하거나 생략(skipped) 가능 — manifest note에 이유 기록.
- 산출: 확정된 핵심 세그먼트, 검증/기각된 가설 목록, "3차 인터뷰 대상 페르소나" 후보.

### 3차 포커스 인터뷰 (Focus) → phase3-focus.md

- 목적: 핵심 페르소나 4~6명 심층 인터뷰로 "왜"와 재현 조건 확보.
- 권장 구조(경험 조사형): 스크리너 → 워밍업 → 정의 끌어내기 → **결정적 경험 재구성**(장소·상대·계기·결정적 순간·전후 변화, 대사 단위) → counter-case → 운영 변수 → 재방문/추천 트리거 → closing.
- GOAL이 카피/오퍼 설계면 통증→욕망→반론 해체→성공기준(하한/상한) 블록 구조로 대체 가능.
- **실행 모드 2가지** (응답자별로 선택, 혼용 가능):
  - **배치 모드** (커버리지 기본): 인터뷰 가이드를 `persona-respondent` 서브에이전트로 디스패치. 단, 3차는 캐릭터 충실도가 관건이므로 **1디스패치=1페르소나** (1·2차처럼 10명 묶음 배치 금지).
  - **대화형 모드** (사람이 직접 파고들 때 기본): `nemotron-personas-korea:persona-interviewee` 스킬을 **그대로** 사용 — Claude가 특정 페르소나 1명을 연기하고 사용자가 인터뷰어가 되어 직접 질문. 대괄호 `[...]`는 캐릭터 밖 지시. A/B 반응 청취(시안 두 개를 보여주고 어느 쪽이 왜 통하는지), 고정 가이드로 예측 못 하는 꼬리 질문, 사용자가 "직접 얘기해보고 싶다"고 할 때 이 모드. **종료 후 반드시 대화 내용을 phase3-focus.md(또는 raw/interview-N.md + 요약)로 옮겨 적는다** — 기록은 채팅 로그가 아니라 프로젝트 디렉터리에 남아야 함.
- 산출: 페르소나별 인터뷰 전문(길면 raw/에 저장 후 링크), 인용 가능한 날것 문장 모음, K별 결론.

### 전체 요약 → summary.md

후속 작업이 이 파일 하나만 읽어도 되도록 작성:
- GOAL과 최종 결론 (결정 권고 포함)
- K별 핵심 발견 (각 3줄 이내) + 근거 phase 파일 링크
- 인용할 만한 날것 문장 top 5~10
- 후속 작업 제안 (downstream_hints 갱신)

## 페르소나 응답 수집 ([FREE] — 가용 수단에 맞게)

- **우선**: `nemotron-personas-korea` 플러그인이 설치된 환경이면 그 스킬들을 사용한다 —
  `dataset`(스키마·샘플링), `dispatch-strategy`(병렬 디스패치 전략), `persona-respondent` 서브에이전트(응답 생성),
  `bulk-reply-save`(3개 이상 응답 파일 일괄 저장), `synthetic-population-validity`(실집단 대비 타당성 점검).
  세그먼트 정의(나이·직업·지역·혼인 등)와 매칭되는 페르소나를 데이터셋에서 샘플링해 응답자로 쓴다.
- **플러그인이 없으면**: 기존 deep-customer-insight 방식(가상 페르소나 직접 설계)으로 대체.
- [HARD] 가상 페르소나 기반 결과에는 반드시 디스클레이머 포함:
  `※ 본 결과는 가상 페르소나 시뮬레이션입니다. 실제 사용자 검증을 대체하지 않습니다.`

## [FREE] 데스크 리서치 — 웹·유튜브 외부 근거 수집 (최신순 우선)

어느 단계든 페르소나 작업 전에(또는 병행으로) K를 공개 근거로 뒷받침할 수 있다. GOAL이 빠르게 변하는 시장(AI 도입, 규제, 플랫폼 기능, 경쟁사 동향)과 닿아 있으면 데스크 리서치를 먼저 돌린다 — 페르소나 시뮬레이션은 지난 분기에 바뀐 것을 모른다.

- **최신성 우선 [인용 시 HARD]**: 최근 12개월 내 자료를 우선하고, 인용하는 모든 주장에 발행일을 명기한다. 확보 가능한 최신 자료가 그보다 오래됐으면 명시한다("최신 확인 가능 자료: YYYY-MM"). 날짜 없는 주장을 현재 사실처럼 쓰지 않는다.
- **소스**: WebSearch → 인용 전 WebFetch로 URL 검증(미검증 URL 인용 금지). 유튜브는 실무자 강연·튜토리얼용(최소 제목·채널·업로드일 확보, 가능하면 페이지 fetch로 스크립트). 최신 30일 여론이 필요하면 last30days류 스킬이 설치돼 있을 때 활용.
- **저장**: 발견은 프로젝트 디렉터리의 `desk-research.md`에(분량이 적으면 해당 phase 파일 안 `## 데스크 리서치` 섹션도 가능), 발견마다 대상 K + 출처 URL + 날짜 태그. manifest `external_data`에 이 패스를 등록하고 `"scope"`에 뒷받침하는 K를 기재 — 데스크 리서치도 외부 근거이므로 실데이터 도착과 같은 절차를 따른다.
- **역할 분담**: 데스크 리서치는 사실(시장 규모, 규제 일정, 기능 유무)을, 페르소나는 반응(인식, 도입 장벽, 워딩)을 담당한다. 검색으로 확정할 수 있는 사실형 K를 페르소나에게 "답하게" 하지 말고, 검색 결과가 세그먼트의 감정을 안다고 주장하게 하지도 않는다.

## [HARD] 외부 데이터 통합 — 실데이터가 도착하면

합성 페르소나 결과는 잠정치다. 실측 데이터(현장 설문, VOC, 실제 인터뷰 녹취, 판매 통계 등)가 언제 들어오든 — 프로젝트 종료 후라도 — 다음 절차로 반영한다:

1. 원본 파일을 프로젝트 디렉터리의 `external-data/`에 저장 (phase 파일에 인라인 금지).
2. manifest에 `external_data` 배열 항목 추가:
   `{ "file": "external-data/현장설문-0815.xlsx", "received": "YYYY-MM-DD", "scope": "관련 K/주장", "integrated": false, "note": "" }`
3. **덮어쓰기 전에 대조**: 영향받는 합성 발견마다 실데이터와 비교해 `confirmed / corrected / overturned / not-covered`로 판정. 격차가 진짜 신호인지 표본 노이즈인지는 `synthetic-population-validity` 스킬의 통계(마진·분포형태·결합구조 비교)로 판단.
4. phase 파일은 **추가 방식으로만 수정** — `## 외부 데이터 검증 (YYYY-MM-DD)` 섹션을 덧붙여 판정을 기록하고, 원래 합성 결론을 몰래 고쳐 쓰지 않는다 (감사 추적이 목적).
5. 판정에 따라 summary.md 결론을 갱신하고 `## 개정 이력`에 한 줄 추가, manifest의 `integrated: true`로 전환.
6. 실데이터로 confirmed된 주장은 **그 주장에 한해** 가상 시뮬레이션 디스클레이머를 뗄 수 있다. 나머지는 유지.

## [FREE] 커스텀(비-데이터셋) 페르소나로 대화형 모드 사용하기

`nemotron-personas-korea:persona-interviewee`는 데이터셋 행을 전제로 만들어졌지만, 같은 대화형 메커니즘을 데이터셋에 없는 손수 설계한 이해관계자(내부 역할, 특정 회사 직원, B2B 의사결정자)에게도 그대로 쓸 수 있다:

- `uuid:`/인구통계 필터 파싱을 아예 건너뛴다. 대신 "커스텀 페르소나 — 데이터셋 아님"이라고 명시하고, 이름·나이·소속/역할·전문 배경·관련 경험 수준·인터뷰 맥락을 인라인으로 완전히 기술한 인자 하나를 넘긴다 (로더가 평소 `=== field ===` 블록으로 내놨을 정보 전부).
- Claude는 이 인라인 프로필을 로드된 페르소나로 취급하고 문서화된 절차(로드 안내 → 세팅 확인 → 첫 질문 대기 → 대괄호 규약)를 그대로 따른다.
- 디스클레이머와 phase3-focus.md 기록은 동일하게 적용 — 커스텀 페르소나도 실제 응답자가 아니다.
- GOAL이 Nemotron의 일반 한국 성인 인구통계로는 대표할 수 없는 특정 조직/역할(내부 팀원, 지목된 상대방, 니치 전문직)에 관한 것일 때 이 방식을 쓴다. 넓은 일반 대중 세그먼트라면 데이터셋 실제 행을 우선 — 데이터셋의 강점은 수작업으로 흉내 낼 수 없는 검증된 현실성이다.

## [HARD] 품질 게이트

- 모든 시뮬레이션 인터뷰에서 페르소나 간 의견 충돌/반박이 드러나야 한다 — 전원 동일 의견은 실패로 간주하고 재수행.
- 각 phase 파일 상단에 GOAL·대상 K·사용 페르소나 수·방법 요약 헤더를 넣는다 (후속 소비자가 맥락 없이 읽어도 되게).
- 단계를 건너뛰거나 병합했으면 manifest note에 이유를 남긴다.
