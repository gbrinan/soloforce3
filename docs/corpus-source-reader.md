# 원본 접수와 구조 문맥 읽기

20 MiB는 일반 가져오기 API의 처리 한도입니다. 별도 접수 경로는 큰 원본을 먼저 검증·보관하고, 분석이 끝난 뒤 검색 자료에 반영합니다. 1,200자 조각은 검색 후보를 찾는 용도로 유지하며, Wiki 분석과 Ask에는 그 조각이 속한 구조 단위를 전달합니다.

## 사용 흐름

1. 설정 → 데이터 → 자료 가져오기에서 로컬 파일을 선택하고 **원본 나누어 올리고 보존하기**를 누릅니다. 파일은 4 MiB씩 올라갑니다. 연결이 끊기면 같은 원본을 다시 선택해 **업로드 재개**를 누릅니다. 이미 올라간 부분의 해시까지 비교하므로 동명 파일의 다른 내용을 이어 붙이지 않습니다.
2. 접수 목록이 **원본 보존 · 분석 대기**가 되면 **분석 시작**을 누릅니다. 기본 250개 구조 단위마다 위치를 저장하고 다음 묶음을 자동 처리합니다. **잠시 멈춤**으로 중단하거나 서버를 재시작한 뒤 **분석 이어가기**를 누를 수 있습니다.
3. 분석이 완료되면 보존한 자료 목록에 새 판이 나타납니다. 분석이 실패하거나 더 최신 판이 이미 등록돼 있으면 기존 검색 자료를 바꾸지 않습니다. **확인 필요**의 이유를 확인하고 보존 원본에서 처리 범위를 나눕니다.
4. 검색 결과의 **절·표의 문맥 함께 읽기**를 엽니다. Wiki 후보는 검색 조각 대신 전체 절·슬라이드·표 행을 선택합니다. 입력 예산을 넘는 단위는 별도 보류 목록에 남습니다.

원본 보존 완료는 본문·이미지의 해석 완료가 아닙니다. 이미지·스캔·음성·영상은 원본이 남아도 OCR·전사 등이 필요합니다. Office 이미지와 PDF 표·레이아웃의 해석 한계도 표시합니다.

## 서로 다른 한도

| 단계 | 현재 한도·동작 |
|---|---|
| 원본 접수 | 파일 512 MiB, 부분 업로드 4 MiB, 설치당 접수 100건·예약 원본 합계 8 GiB |
| 일반 가져오기 API | 원본 20 MiB, PDF 300쪽, Office ZIP 해제 합계 64 MiB 등 기존 제한 유지 |
| 별도 분석 프로세스 | 한 번에 한 작업, 묶음당 기본 250단위, 각 자식 프로세스 120초 제한 |
| 별도 분석 자원 | Node JS heap 512 MiB, ZIP 해제 합계 256 MiB·5,000개 엔트리, PDF 최대 5,000쪽 |
| 별도 분석 결과 | 본문 누계 800만 JS 문자, 구조 단위 5만 개, 검색 조각 10만 개가 상한. 형식별 파서 제한이 먼저 적용될 수 있음 |
| 큰 텍스트 | 20 MiB 초과 TXT·MD·CSV·TSV는 스트림 디코딩. 한 줄/CSV 레코드/단일 절 200만 JS 문자 초과는 보류 |
| 검색 | 조각 1,200 JS 문자, 120자 겹침. 설치 전체 검색 대상 10만 조각 한도 유지 |
| 검색 후 문맥 | 한 부모 단위 UTF-8 64 KiB. Ask 전체 본문 약 23,000 JS 문자 예산. 한도를 넘는 단위는 통째로 보류 |
| Wiki 요청 | 기본 24,000자 및 직렬화 JSON 96 KiB. 프롬프트·메타데이터 포함. 실제 토큰 수는 미측정 |
| 벡터 색인 | 요청당 최대 128조각, 16조각마다 체크포인트. 완성 후 검색 반영 |

위 수치는 무제한 처리나 최대치 성능을 보장하지 않는 상한입니다. JS heap 제한은 Buffer와 외부 메모리를 포함한 전체 프로세스 RSS 제한이 아닙니다. 512 MiB 파일의 최악 조건·동시 부하는 측정하지 않았습니다. 파서 실패·시간 초과·예산 초과는 원본을 지우거나 일부를 읽었다고 전체 성공 처리하지 않습니다.

접수 기록과 원본은 자동 삭제하지 않으므로 100건/8 GiB에 도달하면 보관 정리가 필요합니다. 자동 보관 만료·삭제 UI는 아직 없습니다. 서버를 멈추고 전체 `history/`를 별도 비공개 디스크에 복사·검증한 뒤, 접수 폴더의 원본이 검색 자료나 백업에 있는지 확인해 관리합니다. API에 임의 경로를 전달해 삭제할 수는 없습니다.

## 구조 단위가 의미하는 범위

| 입력 | 보존하는 구조 단위 | 별도 원문 검토가 필요한 부분 |
|---|---|---|
| Markdown·일반 본문 | 제목 경계의 전체 절, 상위 제목 경로 | 다른 절의 예외·각주·참조 조건 |
| CSV·TSV·XLSX | 헤더를 붙인 전체 행과 셀 값 | 병합 셀·다중 헤더·표 밖 각주·수식 의미 |
| DOCX | Heading 스타일 기준 절과 단순 표 행 | 스타일 없는 절, 텍스트상자, 각주·레이아웃 |
| PPTX | 슬라이드 본문과 표 행 | 이미지·도형의 의미, 슬라이드 간 조건 |
| HWPX | 섹션 본문 | 복잡한 표·레이아웃 |
| PDF | 페이지 본문 | 페이지 간 문장·표 연결, 숫자·표 경계 |
| Notion | 개별 블록 또는 헤더가 있는 표 행 | 다른 블록의 조건·첨부·하위 페이지 |

`SourceUnit`은 원문을 다시 읽을 수 있는 구조 단위입니다. 논리적 완결성이나 사실 승인을 증명하지 않습니다. 작은 검색 청크에서 예외가 잘리는 문제를 줄이지만, 다른 절에 있는 예외를 모두 찾았다고 단정하지 않습니다. 큰 Markdown의 표는 스트림 경로에서 절 원문에 남으며 별도 행·열 추출은 하지 않습니다.

표 셀 배열은 구조 단위에 한 번 저장합니다. 긴 행이 여러 검색 조각으로 나뉘어도 각 조각에 전체 셀 배열을 반복 저장하지 않습니다. Wiki 요청에는 헤더와 행 내용이 이미 포함된 본문을 보내며 셀 배열을 중복 첨부하지 않습니다.

## Drive와 Notion

Drive의 일반 바이너리 파일은 `Range` 다운로드로 4 MiB씩 보관·재개합니다. 전후 버전·크기·형식, 제공되는 경우 MD5를 확인하고 최종 원본 SHA-256을 저장합니다. 부분 응답을 지원하지 않거나 전송 중 원본이 바뀌면 중단합니다. Drive 출처로 접수한 작업에는 로컬 업로드 API로 임의 바이트를 넣을 수 없습니다.

Google Docs·Sheets·Slides의 `files.export`는 여전히 10 MB 한도이고 부분 다운로드를 지원하지 않습니다. 별도 접수 기능이 이 공급자 제한을 제거하지 않습니다. 큰 원생 문서는 사용 가능한 내보내기 방법으로 파일을 받은 뒤 로컬 접수하거나 원본에서 범위를 나눠야 합니다. [Google 공식 다운로드 문서](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

Notion의 페이지 읽기 범위·2,000블록 등의 기존 한도는 유지합니다. 첨부 파일의 임시 URL은 원본 백업이 아니므로 필요한 첨부는 파일로 별도 접수합니다. 새 서비스·계정·유료 API는 필요하지 않습니다.

## 보존과 재개

```text
history/
  corpus-intake/<jobId>/
    intake.json               # 출처, 파트 해시, 상태, 원본 해시, 기준 판
    original.bin              # 파싱 전에 보관
    checkpoint.json           # 마지막 완료 단위, 누적 본문 크기
    units/000001.json          # 구조 단위와 검증 해시
    result.json
  corpus/<sourceId>/<revision>/
    original.bin              # 같은 파일시스템은 hard link, 불가하면 복사
    snapshot.json             # units + chunks(unitId 참조)
    vector-progress-*.json   # 재개 가능한 파생 캐시
    vectors-*.json            # 완성 캐시
```

분석 재개 시 저장된 단위를 중복 저장하지 않습니다. 다만 현재 파서는 그 위치를 찾기 위해 앞부분을 다시 읽을 수 있어, 완전한 임의 위치 접근이나 모든 형식의 일정한 처리 속도를 보장하지 않습니다. 파서 버전이 바뀐 작업은 기존 체크포인트를 억지로 이어 쓰지 않고 새 접수가 필요합니다.

`corpus-1` 스냅샷의 기존 검색·백업은 유지합니다. 새 Wiki 준비와 Ask 문맥 확장은 구조 단위가 필요하므로 보존 원본을 재등록합니다. 기존 원본·후보·이전 판을 자동 마이그레이션하거나 삭제하지 않습니다.

개별 자료 ZIP은 원본 합계 100 MiB 한도가 있습니다. 큰 원본 한 개는 접수 목록의 **보존한 원본 받기**로 스트리밍 다운로드합니다. 기존 전체 ZIP 백업 구현은 메모리를 사용하므로 큰 자료실은 서버를 멈춘 뒤 `history/` 폴더를 통째로 복사하고 복사본 해시를 검증하는 방식을 사용하세요. 일관된 체크포인트 백업을 위해 진행 중 분석도 먼저 멈춥니다.

## 검증 명령

```bash
npm run build
npm run test:corpus
npm run test:wiki
npm run test:google-readonly-connection
```

`test:corpus` 안에 `test:corpus-reader`가 포함됩니다. 실제 20 MiB 초과 PPTX·CSV, UTF-16·개행 포함 CSV, 원본 읽기 검증, 중단·재개, 최신 판 충돌, 권한 회수, 표 중복 제거, 1,002개 합성 벡터의 실패·재개를 검사합니다. 실제 서버 검사에서는 HTTP 접수와 Ask의 전체 절 전달/예산 초과 보류를 확인합니다. 실제 LLM 의미 품질, 실제 OAuth, Windows 실행은 해당 환경에서 별도로 검증합니다.
