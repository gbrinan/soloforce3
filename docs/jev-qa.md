# Jev QA 분류

Jev는 기존 자동 QA 대상의 검증 유형(code/document/data/general)을 선택한다. QA 실행 여부, 최종 통과, 승인·권한은 결정하지 않는다. 협업 상태·파일 분리와 기존 CLI/PTY 실행은 유지한다.

## 실행 흐름

기존 QA 트리거 → 산출물 실존/mtime precheck → 검증 유형 선택 → 기존 QA 워커 실행.

- 코드 변경이 있거나 변경 판정이 불가능하면 Jev 호출 없이 코드 검증을 유지한다.
- 코드 변경 0건인 기존 QA 대상만 분류한다. 요청과 보고서가 모두 있어야 한다.
- 문서: 요구사항, 원출처, 범위, 모순 검증.
- 데이터: 원자료, 독립 재계산, 단위·기간, 누락·중복 검증.
- 일반: 요청 충족, 관찰 가능한 결과, 근거, 검증 한계 확인.
- QA 중 코드 변경을 발견하면 분류와 관계없이 코드 검사를 수행한다.
- 실패·낮은 신뢰도·미설정·과대 입력이면 기존 코드 검증으로 복귀한다. QA를 생략하지 않는다.

## 설정

서버 환경변수에 다음을 설정하고 평소 운영 절차로 재시작한다. 키는 저장소에 커밋하지 않는다.

```dotenv
QA_JEV_ENABLED=true
TYPESAFE_API_KEY=<운영 환경에 주입>
QA_JEV_MODEL=jev-latest
QA_JEV_TIMEOUT_MS=3000
QA_JEV_MIN_CONFIDENCE=0.85
```

기본은 비활성이다. `QA_JEV_ENABLED=false`로 되돌리면 기존 QA 검증으로 복귀한다. 제한 시간은 10~10000ms, 신뢰도 임계값은 0.5~1 범위다. 임계값 0.85는 초기 운영값이며 정확도 보증이나 업무 표본으로 보정한 수치가 아니다.

활성화 시 대상 작업의 원래 요청(최대 4000자)과 완료 보고서(최대 12000자)를 TypeSafe API로 보낸다. 파일 본문을 추가로 읽어 보내지 않지만 요청·보고서에 포함된 업무 정보는 전송된다. 초과 입력은 잘라 분류하지 않고 호출을 생략한다. 호출은 1회, 자동 재시도는 0회다. 기존 CLI 구독 외에 Jev 사용 비용이 발생할 수 있다. 전체 비용 절감은 실측해야 한다.

`history/audit.jsonl`의 `qa.profile_selected`에는 작업 ID, 유형, 사유, 소요 시간, 응답 모델, 신뢰도, 토큰 수가 기록된다. 키와 요청·보고서 원문은 이 이벤트에 기록하지 않는다. 운영 평가에서는 분류 정확도, fallback 비율, QA 소요 시간, 재작업률, 전체 비용을 함께 비교한다.

## 검증

```sh
npm run test:qa-jev
npm run test:qa-jev-smoke
npm run build
```

계약 테스트는 로컬 HTTP 서버를 사용한다. smoke는 임시 MYCREW_HOME/WORKSPACE_ROOT와 모의 HTTP 응답·워커를 사용하여 실제 작업 완료 및 QA 생성 경로를 실행한다. 실제 Jev 품질·계정 인증·운영 배포를 검증하는 테스트는 아니다.

## 설계의 한계와 대안

분류가 단순한 업무에서는 규칙 기반 선택이 더 싸고 예측 가능할 수 있다. Jev를 전 작업의 필수 단계로 확대하기 전에 실제 표본에서 규칙과 비교한다. 이번 도입은 기존 QA 수행 대상 안에서 검증을 적합하게 만드는 첫 단계이며, QA 샘플링/면제 정책이나 재검증 루프를 변경하지 않는다.

공식 계약: [TypeSafe API](https://docs.typesafe.ai/api), [Quickstart](https://docs.typesafe.ai/introduction/quickstart).
